# Сайты .i2p через Hydrat

I2P — отдельная необязательная служба для сайтов `.i2p`. Она не участвует в выборе VLESS/Tor-маршрутов обычного интернета. Доступ разрешается отдельно для каждого WireGuard-клиента; по умолчанию он выключен.

## Установка

В версии 1.2.0 доступны готовые образы для amd64 и arm64. Необязательная служба использует образ `ghcr.io/only-hydrat/hydrat:1.2.0-i2p`. Из корня проекта с настроенным `.env`:

```sh
docker compose -f docker-compose.yml -f docker-compose.i2p.yml pull
docker compose -f docker-compose.yml -f docker-compose.i2p.yml up -d
```

Используйте одинаковую версию шлюза, контроллера и I2P-службы. Для другого совместимого образа задайте `HYDRAT_I2P_IMAGE` в `.env`. При последующих обновлениях сохраняйте `-f docker-compose.i2p.yml` в команде Compose.

Для разработки и самостоятельной сборки добавьте оба dev-файла:

```sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  -f docker-compose.i2p.yml -f docker-compose.i2p.dev.yml up -d --build
```

В разделе «Клиенты» включите «Доступ к .i2p». В «Система → Сайты .i2p и адресная книга» доступны статус, ручной прогрев, длительность ожидания и адресная книга. После включения клиента Hydrat предварительно запускает I2P.

## Браузер

1. Подключитесь через WireGuard и сохраните DNS из выданного Hydrat конфига.
2. Если браузер использует свой DNS через HTTPS, отключите его для этого подключения. Системный частный DNS также не должен обходить DNS шлюза.
3. Откройте полный адрес, например `http://имя.i2p/`, чтобы браузер не отправил его в поиск. Для имени нужна запись в адресной книге; стандартные публичные адреса `.b32.i2p` работают без неё.

Отдельное I2P-приложение и прокси в браузере не нужны. Поддерживаются веб-сайты по TCP. Это не поддержка произвольных I2P-приложений, входящих сервисов или UDP. Cookies и отпечаток обычного браузера сохраняются.

## Сон и прогрев

По умолчанию i2pd работает ещё два часа после использования, затем процесс останавливается. Время настраивается от 15 минут до 24 часов. Активные клиентские соединения удерживают его запущенным; после их закрытия отсчёт начинается заново. Проверки состояния, обычный VPN-трафик и фоновые подписки таймер не продлевают.

После остановки остаётся небольшой процесс управления. Запрос разрешённого клиента к `.i2p` или соединение с ранее выданным IP запускает i2pd. Сохранённая информация о сети помогает старту, но туннели строятся заново: мгновенное открытие после сна не гарантируется. При долгом первом открытии дождитесь прогрева и перезагрузите страницу. Статус «Прогрет» означает готовность клиентских туннелей, а не доступность каждого сайта.

## Адресная книга

При первом запуске шлюз однократно добавляет 71 имя из [официального hosts.txt I2P](https://github.com/i2p/i2p.i2p/blob/53002765a300547a2c663ac3c8d50a1b7c56cf1e/installer/resources/hosts.txt). Список встроен в Hydrat, доступ к GitHub при запуске не нужен. Адрес форума в нём — `http://i2pforum.i2p/`, а не `forum.i2p`. Существующие записи имеют приоритет, удалённые имена после перезапуска не возвращаются. Если книга заполнена, добавляются только помещающиеся записи. Наличие имени не гарантирует, что сам сайт сейчас работает.

- Ручные записи принимают имя `.i2p` и публичный Destination либо стандартный `.b32.i2p`.
- Импорт `hosts.txt` сначала показывает ошибки и конфликты. Замена известного адреса требует подтверждения.
- Экспорт сохраняет исходный публичный Destination, если он был предоставлен. Записи, заданные только через B32, экспортируются как `имя=B32`; это расширение Hydrat, которое другие I2P-клиенты могут не понимать.
- Подписки принимают публичный HTTPS на порту 443 или HTTP(S) внутри I2P. Фоновое обновление выполняется не чаще раза в шесть часов и только при работающем I2P. Ручное обновление может запустить прогрев и выполняется в фоне.
- Новые имена добавляются автоматически. Изменения известных имён попадают в список конфликтов. Ручные записи имеют приоритет; удаление подписки не удаляет уже принятые адреса.

Размер импорта или ответа подписки ограничен 1 MiB, книга — 1024 именами, число подписок — десятью. Новые виртуальные адреса ограничены отдельным бюджетом на клиента; уже выданные адреса остаются доступными при исчерпании этого бюджета. Смена Destination выдаёт новый виртуальный IP и закрывает соединения к прежнему адресу. Старые IP не переиспользуются. Сохраняйте книгу вместе с данными шлюза; её удаление не является безопасным способом сбросить настройки.

Адреса и конфликты показываются страницами; поиск охватывает всю книгу. Общий объём сохранённых конфликтов ограничен 1 MiB. Если обновление превышает лимит, оно отклоняется с ошибкой, прежние данные сохраняются. Разберите накопленные конфликты и повторите обновление.

Если порт I2P-моста `19447` пересекается с настроенными портами Xray или Tor, отключается только I2P; обычный VPN продолжает использовать свои порты. Причина записывается в журнал шлюза.

## Отсутствие ретрансляции

i2pd запускается с `notransit=true`, `floodfill=false`, `share=0`. UPnP, публичная консоль, интернет-outproxy и входящие I2P-сервисы выключены. Порты контейнера не публикуются на хосте, Docker socket ему не передаётся. Периодически проверяется число транзитных туннелей; ненулевой результат или ошибка проверки останавливает I2P. Tor остаётся клиентом без relay/bridge.

Это запрещает передачу чужого транзитного трафика, но не скрывает факт использования I2P: соседние узлы видят IP шлюза. Собственные соединения используют чужие узлы сети. Запрет транзита сам по себе не задаёт многократное снижение скорости; фактическая скорость зависит от выбранных туннелей, сайта, сети и ресурсов контейнера. Ограничения по умолчанию: 0,5 CPU и 384 MiB памяти.

## Изоляция и диагностика

`.i2p` не передаётся внешним DNS, включая AAAA/HTTPS/SVCB. Обычные запросы DNS, `.onion` и `.i2p` имеют отдельные очереди. Виртуальные адреса I2P находятся в `198.19.0.0/16`, новые onion-адреса — в нижней половине исходного диапазона. Если сохранённый onion-адрес уже занимает диапазон I2P, I2P не включается; существующий onion-доступ сохраняется.

```sh
docker compose -f docker-compose.yml -f docker-compose.i2p.yml logs --tail 100 i2pd
docker compose -f docker-compose.yml -f docker-compose.i2p.yml exec i2pd \
  curl --fail --silent --unix-socket /run/hydrat-i2p/control.sock http://localhost/status
```

Если I2P остановлен после ошибки проверки, сначала изучите журнал. После устранения причины перезапустите только службу `i2pd`. При отсутствии доступа к счётчику транзита Hydrat не продолжает работу вслепую.

Сон I2P не делает основной `/api/ready` нездоровым. Ошибка отдельного сайта не меняет обычный маршрут клиента. Для автоматических проверок используются тесты Go/Node, изолированный VPN-стенд `scripts/test-onion-integration.sh` (включает I2P-мост с локальным SOCKS) и `scripts/test-i2p-integration.sh` — отдельный тест публичной сети через настоящий Xray и i2pd. Последний обращается к публичному I2P-сайту и создаёт временные контейнеры, которые удаляются после проверки. Локальный SOCKS-стенд сам по себе не доказывает доступность публичной I2P-сети.

Параметры маршрутизатора: [документация i2pd](https://docs.i2pd.website/en/latest/user-guide/configuration/).
